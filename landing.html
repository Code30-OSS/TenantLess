The problem

Testing anything that reads an Azure estate leaves you two bad options.

TenantLess is the third: a tenant you specify — then scan it, break it, regenerate it, and get the same thing back tomorrow.

Option A

Point at a real tenant

Expensive, slow, irreproducible — and it only contains the problems it happens to have.

Option B

Hand-write fixtures

Reproducible, but they encode only what you already thought of — at a scale that never exposes what scale actually breaks.

TenantLess

A tenant you specify

Ask for 300 subscriptions, hub-and-spoke topology, an 8% rate of public-blob storage, and a long tail of resource types — then generate it, deterministically.

Who it's for

The axis isn't company size — it's who owns the estate you read.

Not headcount, not cloud spend. The only question that decides it: does the infrastructure your code inspects belong to you, or to someone else?

Rarely worth it

You read your own estate

Platform teams, internal FinOps, in-house governance tooling. Your estate is your test data — your dev subscription already looks like your prod, and it's free to read. TenantLess helps only at the margin: rehearsing a tooling change before you point it at prod.

Structurally necessary

You read someone else's estate

Scanner and CSPM vendors, FinOps SaaS, governance products, consultancies with their own tooling. You have N customers, N estates — and you can reproduce none of them. You can't borrow a client's prod to debug. A tenant you specify is the only way to reproduce a customer-reported bug.

Enterprise vocabulary, but not an enterprise-only tool. The project speaks in 300 subscriptions, landing zones and CAF archetypes, so it reads like it's for big companies. But the population that structurally needs it is vendors and consultancies — and that includes three-person studios. A studio shipping an Azure cost tool has this problem on day one, harder than a large vendor who can afford sandbox tenants.

Training & enablement

Every trainee, the same realistic estate.

Teaching FinOps, SRE and DevOps means practising on infrastructure — but prod is risky, and no two people can safely share it. TenantLess hands everyone a byte-identical estate, reset in seconds between cohorts, with no real identifiers anywhere.

A live Azure estate — without an Azure bill.

The same 145K-resource tenant, the same 18 violation types, the same cost story — for 5 engineers or 500. Universities and bootcamps get a real estate to teach on; teams onboarding at scale get a safe range where breaking things has no blast radius.

  • FinOpsCost allocation, anomaly hunting and chargeback against a real cost fact table.
  • SRE & DevOpsFind and remediate violations, then practise drift detection and revert on a tenant that resets.
  • Governance18 injectable violation types across severities — a graded range for audit and policy training.

What it serves

Seven planes of a real estate — over the covered ARM surface.

List, detail and $filter with pagination and ARM CloudError shapes — the surface a discovery scan actually exercises, not all of Azure ARM.

01 / management

ARM

List / detail / $filter with pagination and arbitrary-depth nested resource types.

02 / finops

Cost Management

Cost Management Query API served over a generated cost fact table.

03 / identity

AAD / Entra

Token issuance (RS256/JWKS), 8 built-in RBAC roles, assignments, injectable over-privilege.

04 / drift

Configuration drift

Deterministic drift a re-scan detects — and can revert.

05 / topology

Cross-subscription

Hub-spoke peering, shared Key Vaults, centralized logging, shared registries, private endpoints.

06 / governance

Violations

18 injectable violation types across severities, at rates you control.

07 / console

Web UI

Generate, snapshot, restore and inspect estates in the browser, plus a scanner demo.

Architecture

A profile in. A synthetic tenant out. Served over REST.

The data boundary is enforced end-to-end: the analyzer distills distributions, never raw identifiers — held to a denylist scan, minimum-aggregation thresholds and per-extractor leak tests.

Python

Seed Analyzer

Distills a scan into a statistical profile — distributions, archetypes, co-occurrence. Never raw identifiers.

→
Python

Generator

Inverts a profile into a full synthetic tenant, written to PostgreSQL via binary COPY.

→
Rust

ARM Mock Server

Serves it over ARM-compatible REST so an existing scanner walks it unmodified — plus the web console.

Quickstart · one command

A populated tenant in about 12 seconds.

Requires only Docker — no host Python, Node or Rust. Compose brings up PostgreSQL, seeds a fixed demo estate, and starts the ARM mock server on it.

bring it up
# PostgreSQL + generator + ARM server
cp .env.example .env
docker compose --profile demo up
scan it like a real tenant
# presence-only Bearer auth by default
curl -H "Authorization: Bearer anything" \
  "http://localhost:8080/subscriptions?api-version=2022-12-01"

// Then open http://localhost:8080/ui for the web console. Your estate is safe on restart — the generator inspects the whole estate under an advisory lock and skips if any of it is already populated.
